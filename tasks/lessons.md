# ReleaseTune 開発の教訓

## Vercel Cronのバッチ処理は「件数」ではなく「経過時間」で打ち切る

- **何が起きたか**: `spotify-backfill` cron（2026-08-19実装）で、外部APIの実測レイテンシを測らずに「1回120件」と件数ベースで上限を決めてしまった。本番で1トラックあたり平均約1.3秒（外部API往復が支配的）かかっており、120件だと理論上約150秒必要なのに対し`maxDuration=60`だったため、毎日Vercelの関数タイムアウトで静かに打ち切られていた（エラーにはならず、ただ処理件数が想定よりずっと少ないだけなので1ヶ月近く気づかなかった）
- **教訓**: サーバーレス関数で外部APIを逐次呼び出すバッチ処理を書くときは、件数の見積もりではなく実測レイテンシ（本番相当の環境で実際に計測した値）から安全な処理件数を逆算するか、そもそも件数ではなく`Date.now()`ベースの経過時間で打ち切る設計にする。`maxDuration`に対して十分なマージン（今回は60秒に対し45秒）を残すこと
- **適用範囲**: このプロジェクトの他のcron（`new-releases`など）や、今後追加する外部API連携バッチすべてに適用する。新しいバッチ処理を書いたら、デプロイ後にレスポンスの所要時間（`elapsedMs`のような実測値をレスポンスに含める）を確認する習慣をつける

## 文体の指定は、言葉だけでなく実例で確認してから量産する

- **何が起きたか**: 楽曲紹介文の文体を「です・ます調」と指定されたため、すべての文を「〜です」「〜ました」で終える執筆ルールにして79記事を書いた。ところが最初のレビューで、ユーザーは短文の「〜のCMソングです。」を「〜のCMソング。」、「〜を記録しました。」を「〜を記録。」、長文の「作曲は菊池一仁です。」を「作曲は菊池一仁。」と体言止めに直した（動詞の「〜ました」は残した）。「です・ます調」という言葉が指していたのは「常体（だ・である）ではない」ことで、名詞文まで「です」で締めることではなかった
- **教訓**: 文体・トーンのように言葉だけでは幅がある指定は、量産の前に2〜3文の実例を見せて確認する。レビューで直された箇所は、元の下書きと並べて差分を確認し（`track_note_drafts.issues` の `edited_by_reviewer` に元の下書きを残してある）、共通する傾向をルールと機械チェックに反映する
- **適用範囲**: 紹介文に限らず、ユーザーが読む文章を大量に生成する作業すべて
