# 楽曲紹介文の作成指示書（Muse 向け）

ReleaseTune（「今日はあの曲のリリース日」をテーマにした日本語の音楽リリースカレンダー）に載せる、楽曲の紹介文を書いてください。紹介文は、その曲を知っている人には当時を思い出すきっかけに、知らない人には聴いてみたくなるきっかけになるものを目指します。

## 受け取るもの

| ファイル | 内容 |
|---|---|
| この指示書（`MUSE.md`） | 作業の進め方と返し方 |
| `STYLE.md` | 執筆ルールの正本。**書き始める前に全部読んでください** |
| 作業ファイル（複数） | 書いてほしい記事（Wikipedia の記事1本＝1件）が並んでいて、回答欄が空になっている。次の2種類がある<br>・`muse-MMDD.json`: その日付（例: `muse-1110.json` は11月10日）にリリースされた曲<br>・`muse-top100-NNN.json`: 2010年以降に Billboard JAPAN の年間 TOP100 に入ったアーティストの曲。同じアーティストの記事はまとまっている（1ファイル30記事まで） |

`STYLE.md` の「入力と出力」に出てくる `pending.json`・`drafts.json` は、この作業ファイルのことだと読み替えてください（回答欄の意味は同じです）。

**書く順番**: まず `muse-MMDD.json` を日付の近いものから（その日のサイトの日付ページや X の紹介に間に合わせるため）、次に `muse-top100-NNN.json` を番号順に。1ファイル書き終えるごとに返してください（全部そろえてから返す必要はありません）。

自動公開を増やすために、次の2点を意識してください（どちらも `STYLE.md` の「事実の扱い」に追加済み）。

- **賞は、曲そのものの受賞と出典ではっきり言えるときだけ書く。** 書いた記事はレビューに回り、公開が遅れます。歌手個人の新人賞や、合算の賞は書かなくてよい
- **出典を一歩も広げない。** 照合でほかの書き手が引っかかったのは、範囲の拡大（「アルバムとして初」→「作品として初」）、題名の省略（「不良1/2」→「不良」）、因果のないつなぎ、「この」で別物を同一視、あいまいな出典の読み切り、どの盤の記録か分からないチャート

## 作業ファイルの項目

### 読むだけの欄（変えない）

- `wiki_title`: 出典の記事名。**返すときに1文字でも変わると取り込めません**
- `wiki_url`: 出典の URL（参考。アクセスしなくてよい）
- `status`: `sourced`＝新規、`rewrite`＝書き直し依頼
- `tracks`: サイトのデータベース上の曲（曲名・アーティスト・発売日）。同じ記事に複数の盤が対応することがある
- `source_text`: Wikipedia の記事を整形した出典テキスト。**書く事実の土台はここ**（ほかの情報源は下の「Wikipedia 以外の情報源」の範囲で補うだけ）
- 書き直し依頼のときだけ: `reviewer_comment`（レビューでの指摘）と `previous`（前回の文面）

### 書く欄

| 欄 | 書くこと |
|---|---|
| `note_short` | 短文。60字以内、1〜2文。日付ページのカードに出る |
| `note_long` | 長文。150〜400字。楽曲詳細ページに出る。出典が薄くて150字に届かないときは `""` のまま |
| `facts` | 書いた事実ごとの根拠。`{"claim": "書いた内容", "source": "source_text の該当箇所をそのまま短く引用"}` の配列。短文・長文に書いた事実はすべて載せる。Wikipedia 以外のページから書いた事実は `"source_url": "ページの URL"` を足し、`source` にはそのページの該当箇所を引用する |
| `skip` | 短文すら書けないとき（出典が別の曲の記事、情報がほぼ空など）だけ `true` |
| `skip_reason` | `skip` を `true` にしたときの理由 |
| `review_note` | （任意）この記事についてレビューで見てほしい点・迷った点。書いた記事は必ず人が確認する。なければ欄ごと省いてよい |

## 進め方

1. `STYLE.md` を読む
2. 作業ファイルの記事を上から順に、1件ずつ書く
   - まず `tracks` と `source_text` を見比べ、出典が本当にその曲の記事か確かめる（別アーティストの同名曲・カバー元の原曲の記事なら `skip`）
   - `rewrite` の記事は `reviewer_comment` の指摘をすべて直す。`previous` のよかった部分は残してよい
3. 全件書いたら、下の「返す前の確認」をすべて確かめる
4. ファイル名の末尾を `.done.json` にして返す（例: `muse-1110.json` → `muse-1110.done.json`）

## Wikipedia 以外の情報源

`source_text` にない事実でも、次のページで確かめられれば書いて構いません（詳しくは `STYLE.md` の「Wikipedia 以外の情報源」）。

| 使ってよい | 使わない |
|---|---|
| アーティスト・レーベル・タイアップ先の公式サイト / Wikidata / MusicBrainz / 英語版 Wikipedia / 日本レコード協会の認定 / Billboard JAPAN・オリコンのチャートのページ | ニュース記事の本文の書き写し / 歌詞サイト / SNS・ブログ・個人サイト・ファンの wiki / 通販サイトの商品説明 / ほかの AI の回答 |

- その事実の `facts` に `source_url` と、そのページからの引用（`source`）を必ず付ける。付いていない事実は `source_text` にあるものとして照合され、見つからなければ誤りとして扱われる
- `source_url` を使った記事は、照合を通っても**必ず人のレビューに回る**（公開まで時間がかかる）。`source_text` だけで十分に書ける記事では使わなくてよい。いちばん役に立つのは、`source_text` が薄くて長文が書けない記事や、タイアップ・認定が抜けている記事
- `source_text` と食い違うときは `source_text` を優先し、食い違いを `review_note` に書く
- 発売日・曲名・アーティスト名がサイトの DB（`tracks`）と違うページは使わない（別の盤や別の曲の可能性がある）

## 特に守ってほしいこと（STYLE.md の要点）

- **根拠のない事実は書かない。** 正しいと知っていても、`source_text` か上の情報源のページで確かめられなければ書かない。自分の知識で補わない
- 数字（順位・枚数・年・回数）は出典の表記どおり。計算して新しい数字を作らない（「発売から◯年」「◯年前」は書かない）
- 出典の文をなぞらない。**出典と21字以上続けて同じ文字列になると機械チェックで指摘されます**。語順と構成を組み替えて自分の言葉で書く
- 文末: 名詞で終わる文は体言止め（「ドラマ『◯◯』の主題歌。」「オリコン最高6位。」）、動詞で終わる文は「〜ました」「〜ています」。「である」「だ」「した」などの常体は使わない
- 短文には曲名・アーティスト名・発売日を書かない（画面に出ている）。優先順位はタイアップ → チャート・売上・認定 → 受賞・紅白 → 作詞・作曲者や制作 → 何枚目の作品か
- 作品名（ドラマ・映画・番組・アルバム）は『』、曲名と CM の商品名は「」。人名は初出をフルネームで、敬称なし
- 使わない: 「Wikipedia」「によると」「年前」、推測（「〜だろう」）、感嘆符（固有名詞の「!」は残す）、絵文字
- 評価語（名曲・代表曲・大ヒット・伝説・不朽・名盤・傑作・国民的・珠玉）は出典に書かれている場合だけ
- 『』「」で囲む名前は、出典テキストか曲名・アーティスト名に出てくる表記どおりに書く
- 「初」「唯一」「最大」「最後」は、出典が限っている範囲（アルバム・シングル・ソロ名義など）ごと書く。題名は省略しない
- 別々に書かれた事実を「〜し、」「〜ため」でつながない。因果は出典に書かれているときだけ
- 「この」「その」で前の文を受けるのは、出典が同じものだと書いているときだけ
- 賞は曲そのものの受賞のときだけ。歌手個人の賞を書くなら受賞者を主語にする（賞を書いた記事は必ず人の確認に回る）
- レーベル名のような長い固有名詞（「コロムビアミュージックエンタテインメント」は20字）は、前後の言い回しを出典と変えれば丸写しの指摘を避けられる。省いてもよい

## 書き終えた記事の例

（`source_url` を使う場合の facts の例: `{"claim": "日本レコード協会のゴールド認定（ストリーミング）", "source": "（認定ページの該当行）", "source_url": "https://www.riaj.or.jp/…"}`）


```json
{
  "wiki_title": "箱根八里の半次郎",
  "wiki_url": "（そのまま）",
  "status": "sourced",
  "tracks": [ "（そのまま）" ],
  "source_text": "（そのまま）",
  "note_short": "デビューシングル。日本レコード協会のトリプル・プラチナ認定。",
  "note_long": "（150〜400字。出典が薄ければ \"\"）",
  "facts": [
    {"claim": "デビューシングル", "source": "氷川きよしのデビューシングル。"},
    {"claim": "トリプル・プラチナ認定", "source": "認定: トリプル・プラチナ（日本レコード協会）"}
  ],
  "skip": false,
  "skip_reason": ""
}
```

見送る記事は `"skip": true, "skip_reason": "出典が同名の別の曲の記事"` のようにし、`note_short`・`note_long`・`facts` は空のままでかまいません。

## 返す前の確認

- [ ] ファイル全体が JSON として正しい（カンマ抜け・引用符の閉じ忘れがない。文中の `"` は `\"` にする）
- [ ] 記事の数と順番、読むだけの欄が受け取ったときのまま
- [ ] `skip` でない記事は、`note_short` が60字以内で「。」で終わっている
- [ ] `note_long` は `""` か150〜400字で、「。」で終わっている
- [ ] 文末に「である」「だ」「した」などの常体がない
- [ ] 数字・作品名・人名がすべて `source_text`（または `tracks`、`source_url` を付けたページ）にある
- [ ] `source_url` を付けた facts の `source` が、そのページにある文のそのままの引用になっている
- [ ] 各文を出典と見比べ、範囲を広げた・つないだ・読み切ったところがない
- [ ] `facts` が空でない（`skip` の記事を除く）

## 返すときに添えてほしいこと

特定の記事について迷った点（例: 出典の中で数字が食い違っていた、タイアップがどの盤に付いているか曖昧だった）は、その記事の `review_note` に書いてください。そのうえで、ファイルと一緒にメッセージで次を短く伝えてください。

- 書いた記事数・見送った記事数（見送りは理由も）
- 記事をまたぐ迷い（複数の記事に共通する判断など）
